# المعمارية
## الاختيار: Supabase (Postgres)
- **الأسباب:** معاملات ذرية وقيود فرادة لمنع التكرار، وعزل بيانات المتاجر عبر RLS، وتقارير SQL، ودعم واتساب كقناة تحقق عبر Twilio.
- **المقابل:** العمل دون اتصال غير مدمج، فنبني طبقة تخزين محلي وطابور مزامنة. الاكتساب والاستبدال يتطلبان الخادم دائمًا.
## الطبقات
1. واجهات العميل والموظف (تطبيق جوال، التقنية تُحسم بنموذج تجريبي في المهمة 1.9).
2. لوحة التاجر ولوحة الإدارة: تطبيقا ويب منفصلان.
3. قواعد العمل: دوال Postgres وEdge Functions، لا شيء منها في الواجهة.
4. الوصول للبيانات: RLS مع صلاحيات أعمدة، وحزمة `private` غير مكشوفة للـ API.
5. العمليات الحساسة: دوال `security definer` بمسار بحث ثابت، وتُمنح للمسجلين فقط.
## مبادئ
- الأدوار: مدير المنصة في جدول `platform_admins`؛ المالك بملكية المتجر؛ الموظف في `merchant_staff`. لا حقل دور يعدّله المستخدم.
- العميل لا يكتب الأرصدة ولا العمليات ولا الرموز. البطاقة تُنشأ عبر `join_program` فقط.
- ساعة الخادم هي المرجع لصلاحية الرموز.
## التسجيل والتحقق (قيد الإعداد)
هاتف: رسالة نصية فقط حاليًا (واتساب مؤجل بقرار المالك). بريد وجوجل يظهران في التطبيق فقط إن فُعّلا في Supabase، ويُشترط هاتف موثّق للاكتساب والاستبدال (`private.phone_verified()`).
